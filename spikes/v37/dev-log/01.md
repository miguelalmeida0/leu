# dev01 — the pre-registered design on the real model (baseline)

**Configuration:** the approved §6 prompts verbatim; the Step 2 reading schema; the pairwise second
opinion; the Step 2 checks and adapter. Only change before it: the first compile's defect fix.

## Before the run: the first real compile and the first real calls

* The Foundation Models engine compiled at the first attempt against the real SDK (macOS 26.6, Xcode
  26.6, Swift 6.3.3); the `canImport` branch is taken, so nothing was stubbed.
* **Architecture defect found by the first calls:** every one-segment answer failed in ~200 ms with
  `ModelManagerError 1032`. Isolated with a standalone probe: the SDK rejects an array schema bounded
  `0…1`; `0…2`, `1…1`, `1…2` and `0…3` work. Every one-segment reading has `links` bounded `0…1`.
  **Fix:** `links` is bounded `0…max(k, 2)` (a one-segment answer cannot have a valid link; V1 already
  drops self-links). Kept: `readings/C-mac-dev01-sdk-error.jsonl`. Error text is now printed with
  `SPIKE_DEBUG_ERRORS=1` (stderr, SDK text only).
* Answer keys: the compile call copies the source claims back as "mistakes"; the self-check rejects
  them (95 of 111 dropped as not opposite). 23 of 34 P targets keep a key, 11 are empty.

## Result

Far below the stop line in every configuration. D asks on 98% of answers and scores only on gold-weak
cases (it calls almost everything "insufficient"): its 37.5% is not discrimination.

## Failure analysis (P and C only)

* **The reader does not discriminate.** Nearly every segment is labelled `partiallyEntails · affirmed`,
  including plain misconceptions ("Authentication is where the app checks what you're allowed to do").
* **The pairwise second opinion says `opposite` to nearly everything**, including C1 and C3.
* **C5 is one segment** ("JWTs are signed so nobody can read them"): the false conclusion is invisible.
* Greedy decoding is not fully deterministic: C4's labels differed between two runs.
